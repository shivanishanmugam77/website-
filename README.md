# Catalogue Platform

Ingest supplier PDF catalogues → AI extracts product images and metadata → an admin reviews,
corrects and approves → approved products appear on a customer-facing catalogue site.

**Current status: Phase 5b, step 1 of 3** — repository, Docker stack, database, authentication (login, roles, audit
log), **catalogue ingestion** (upload supplier PDFs, render every page, extract the embedded product images
at full resolution, background processing with progress tracking), **text recognition** (the text on every
page is read, Chinese + English; model codes / sizes / series labels are picked out; each page is typed) and
**photo panels**: every page is cut into its individual pictures, each with the text that belongs to it,
and an admin can correct the panels by hand (move, resize, draw, delete, undo).
There is no product cut-out (AI detection), full admin UI or customer UI yet; those arrive in later phases
(see [Roadmap](#roadmap)).

## Requirements

* Docker Engine 24+ with Docker Compose v2 (`docker compose`)
* `make` (optional; every target is a thin wrapper around a `docker compose` command)
* ~2 GB free disk for images. No GPU is needed until Phase 5.

## Quick start

```bash
make init        # creates .env with freshly generated SECRET_KEY / POSTGRES_PASSWORD
make up          # builds images, starts Postgres + Redis, applies migrations, starts API/worker/web
                 # (`make up-backend` starts everything except the frontend)
make seed        # inserts default categories and AI-threshold settings (idempotent)
```

Without `make`: `./scripts/init-env.sh && docker compose up -d --build && docker compose run --rm backend python -m app.cli.seed`.

### Verify it is working

```bash
docker compose ps                                  # all services "healthy"; `migrate` exited (0)
curl -s localhost:8000/api/health/live             # {"status":"ok"}
curl -s localhost:8000/api/health/ready            # database + redis both "ok": true
curl -s localhost:3000/healthz                     # {"status":"ok"}   (frontend)
curl -s localhost:3000/api/health/ready            # same JSON as :8000 -> frontend->backend proxy works
docker compose run --rm backend celery -A app.workers.celery_app:celery_app call system.ping
docker compose logs worker | grep -i "ready"       # worker connected to Redis
```

`/api/docs` (Swagger UI) is available in development.

### Run the tests

```bash
make test        # = docker compose run --rm backend pytest
```

The suite needs **real PostgreSQL (with pgvector) and Redis** — the compose services provide both.
It creates and drops its own database named `<POSTGRES_DB>_test` on every run and refuses to run
against any database whose name does not end in `_test`, so your development data is never touched.
SQLite is not supported: the schema uses JSONB, `vector` columns and check constraints.

What is covered: authentication (login, lockout, token rotation and theft detection, logout, password
change, CSRF origin check, role checks, audit trail, admin CLI), configuration validation, structured logging and secret redaction, health/readiness
(including dependency failure → 503), request-id handling, CORS, Celery wiring, every table and
constraint, cascade/`SET NULL`/`RESTRICT` rules, full Catalogue→Page→Image→Object→Segmentation→
Candidate→Product traceability, pgvector search, JSONB queries, seed idempotency, and a **migration ↔
model drift check** plus a full downgrade/upgrade round-trip.

## Configuration

All configuration is environment-driven; see `.env.example` for the full annotated list.
Secrets are generated by `scripts/init-env.sh`, are never committed, and are redacted from logs and
from `repr(settings)`. In `APP_ENV=production` the app refuses to start with a `SECRET_KEY` shorter than
32 characters, and API docs are disabled.

The AI confidence thresholds (`AI_AUTO_REVIEW_THRESHOLD`, `AI_LOW_CONFIDENCE_THRESHOLD`) are read from
the environment **once**, when `make seed` first creates the `app_settings` rows. After that the
database values win, so they can be tuned at runtime without a redeploy. Seeding never overwrites a
value an admin has changed.

## Authentication

* **Sessions:** a 15-minute access token (JWT) plus a rotating 14-day refresh token, both in **HttpOnly,
  SameSite** cookies (JavaScript cannot read them). The refresh token is stored only as a SHA-256 digest, is
  replaced on every use, and replaying an already-used token revokes the whole session (theft detection).
* **Immediate revocation:** the access token is only honoured while its session is live, and the user's role
  and active flag are read from the database on every request, so logout, password change, deactivation and
  demotion take effect at once.
* **Passwords:** argon2id, minimum 12 characters (max 128). Five failed logins lock the account for 15 minutes.
  Unknown email, wrong password, locked and disabled accounts all return the *same* 401 and cost the same time.
* **Roles:** `ADMIN` and `CUSTOMER`. Registration only ever creates customers; admins can only be created from the
  command line.
* **CSRF:** every `POST/PUT/PATCH/DELETE` must carry an `Origin` (or `Referer`) header from a trusted origin
  (`CORS_ORIGINS`; in development also `localhost:8000`, so Swagger UI works). Browsers do this automatically;
  scripts and `curl` must send it, e.g. `-H "Origin: http://localhost:3000"`.
* **Audit log:** logins (successes and failures with the reason), logouts, registrations, password changes and
  token-reuse alerts are recorded; admins read them at `GET /api/admin/audit-logs`. Later phases record every
  admin action through the same service. Secrets are masked before storage.

| Endpoint | Who | Purpose |
| --- | --- | --- |
| `POST /api/auth/register` | anyone | create a customer account and sign in |
| `POST /api/auth/login` | anyone | sign in |
| `POST /api/auth/refresh` | cookie | rotate tokens |
| `POST /api/auth/logout` | anyone | end the session server-side, clear cookies |
| `GET /api/auth/me` | signed in | current user |
| `POST /api/auth/change-password` | signed in | change password, sign out other devices |
| `GET /api/admin/audit-logs` | admin | filterable, paginated audit trail |

### Create the first admin

```bash
docker compose run --rm backend python -m app.cli.create_admin --email you@example.com --full-name "Your Name"
```

It asks for the password with hidden input (12+ characters). To reset an existing admin's password (this also
signs that admin out everywhere) add `--reset-password`.

### Try it

Open **http://localhost:8000/api/docs**, use `POST /api/auth/login`, then `GET /api/auth/me` and
`GET /api/admin/audit-logs`. Or from PowerShell:

```powershell
$h = @{ Origin = "http://localhost:3000" }
$body = @{ email = "you@example.com"; password = "YOUR PASSWORD" } | ConvertTo-Json
Invoke-RestMethod -Uri http://localhost:8000/api/auth/login -Method Post -ContentType "application/json" -Headers $h -Body $body -SessionVariable s
Invoke-RestMethod -Uri http://localhost:8000/api/auth/me -WebSession $s
Invoke-RestMethod -Uri http://localhost:8000/api/admin/audit-logs -WebSession $s
```

### Known limits (deliberate, scheduled)

* No "forgot password" email yet (needs email infrastructure). Admins recover through the CLI.
* Registration has no CAPTCHA or per-IP rate limit, and account lockout can be used to lock a known email
  out for 15 minutes. Redis-based rate limiting is planned for Phase 13.
* Audit-log IP addresses are the socket address unless `TRUSTED_PROXY_COUNT` is set (only do that behind a
  proxy you control; otherwise clients can forge the header).

## Catalogue ingestion

Suppliers send catalogues from time to time; an admin uploads each PDF and the system processes it in the
background. Full details: [`docs/ingestion.md`](docs/ingestion.md).

Until the admin UI exists (Phase 7), use the interactive API page **http://localhost:8000/api/docs**
(sign in with `POST /api/auth/login` first):

1. `POST /api/admin/suppliers` — once per supplier.
2. `POST /api/admin/catalogues` — choose the PDF (and the supplier). Returns immediately.
3. `GET /api/admin/catalogues/{id}` — watch `status`, `processing_progress` and `job` until `COMPLETED`.
4. `GET /api/admin/catalogues/{id}/pages` — one entry per page, with image and thumbnail URLs.
5. `GET /api/admin/catalogues/{id}/pages/{n}/images` — the images found on a page, with their positions.

Also available: `POST .../reprocess`, `DELETE ...`, and filtering/search on the catalogue list.

### Text recognition (Phase 4)

After the pages are rendered the worker reads the text on each one (details: [`docs/text-recognition.md`](docs/text-recognition.md)).
Watch `current_stage` change from `render_pages` to `read_text`, then:

6. `GET /api/admin/catalogues/{id}/pages/{n}/text` — every line read (in reading order, with its position),
   plus the model codes, sizes and series labels spotted in it, and the page's type.

### Photo panels (Phase 5a)

Then the worker cuts each page into its photo panels (details: [`docs/panels.md`](docs/panels.md)).
`current_stage` becomes `find_panels`, and afterwards:

7. `GET /api/admin/catalogues/{id}/pages/{n}/panels` — the panels in reading order: position, a link to each
   cut-out picture, and the text lines (captions, model codes, sizes) that belong to each.
8. `GET /api/admin/catalogues/{id}/pages/{n}/panels/preview` — the page picture with every panel outlined and
   numbered; open it in the browser to check the result by eye.
9. `GET /api/admin/catalogues/{id}/panels/overview` — the same for up to 40 pages at once, as one contact sheet.
10. `GET /api/admin/catalogues/{id}/pages/{n}/panels/editor` — correct the panels with the mouse
    ([`docs/panel-editor.md`](docs/panel-editor.md)). Reprocessing a catalogue that has such corrections is
    refused unless `discard_corrections=true`.

### Product finding (Phase 5b, in progress)

The models that find desks, chairs and cabinets inside a panel are in, together with a command to try
them on a page of a processed catalogue (nothing is saved yet). See
[`docs/product-detection.md`](docs/product-detection.md).

```powershell
docker compose run --rm backend python -m app.cli.download_models
docker compose run --rm backend python -m app.cli.check_products --catalogue <id> --page 8
```

Check the text engine on its own, without any catalogue:

```powershell
docker compose run --rm backend python -m app.cli.check_ocr
```

## Database notes

* PostgreSQL 16 with the **`vector`** (pgvector) and **`pg_trgm`** extensions. The initial migration runs
  `CREATE EXTENSION IF NOT EXISTS` for both; on managed Postgres the migrating role needs permission to do
  so (or an admin must enable them once). The `pgvector/pgvector:pg16` image used here has both.
* Enums are stored as `VARCHAR`, not native PG enums, so adding a value never needs `ALTER TYPE`.
* Embedding dimension is fixed at **512** (`app/core/constants.py`, OpenCLIP ViT-B/32). Changing the
  embedding model to a different size needs a migration.
* No ANN (HNSW) index and no full-text index yet: they are created together with the first queries that
  use them (duplicate detection, Phase 6/10), when there is real data to tune against.
* See [`docs/database.md`](docs/database.md) for the entity diagram and deletion rules.

## Troubleshooting

* **`SECRET_KEY is not set`** on any `docker compose` command → run `make init`.
* **Frontend cannot write `.next`** on Linux → your host UID is not 1000. Rebuild with a matching user or
  `chmod -R a+rw frontend`, then `docker compose up -d --build frontend`.
* **Changed `frontend/package.json`** → `docker compose down`, `docker volume rm catalogue-platform_frontend_node_modules`, `make up`.
* **Port already in use** → change `POSTGRES_PORT` / `REDIS_PORT` / `BACKEND_PORT` / `FRONTEND_PORT` in `.env`.
* **`permission denied to create extension "vector"`** → see *Database notes*.
